# ai-worker-stage-types

A stage type crosses models, services, jobs and views, and is easy to get half-right. Follow the checklist in order. Per-layer rules live elsewhere: `ai-worker-domain` (models, migrations), `ai-worker-orchestration` (jobs/services), `ai-worker-testing` (specs), `ai-worker-ui` (views). This file only lists the touch points. Worked example throughout: `local_test`.

## Lifecycle

`Workflow#status` -> `Workflow#current_stage` (`Workflows::CurrentStage`, using `Workflows::StageResolver`) -> `StageExecutor#call` (guards the live checkout, polls, rescues) delegates to `Stages::StartHandler#call` (with a `Stages::AiRunLauncher`), which dispatches on `stage.stage_type` to a `start_*` method -> `AiRunLauncher#call` spawns a detached agent (`processing: true`, pid/log in `ai_*` columns) -> later scheduler ticks hit `StageExecutor#poll_ai_run`, which delegates to the poller from `Stages::RunTooling` (`AiCli::RunPoller`) -> when done, `finalize_success` hands the output to `Stages::CompletionHandler#call`, which dispatches on stage type to a `Stages::*Finish` service (`ImplementationFinish`, `PrCheckFinish`, `TaskFinish`, `PrReviewFinish`, `JiraLifecycleFinish` for jira_update/uat_test, `LocalTestFinish`, `CiCheckFinish`, `SimpleImplementationFinish`, `CiVerifyFinish`, `PrOpenedFinish` for pr_create, `RunbookStepFinish`) -> the finish service calls `workflow.finish_ai_run!(status: <next>)`, logs a `StageRun` action, runs side effects. Failures go to `Stages::FailureHandler` (via `StageExecutor#fail_stage`).

local_test: `implementing` -> (`Stages::ImplementationFinish` sets `local_testing` when `project.local_test_ready?`) -> `Stages::StartHandler#start_local_test` -> `Stages::LocalTestFinish#call` -> `reviewing`. A failed round feeds `local_test_feedback` to the next `pr_check` run, which may send the workflow back to `local_testing` (`Stages::LocalTestPolicy.retest_after_fix?` in `Stages::PrCheckFinish`).

ci_loop (`Project#flow` `ci_loop`, gated by `Project#ci_loop_ready?`: Jira project + `ci_command`): `Workflows::StageResolver.stage_type_for(..., ci_loop: true)` maps `implementing` to `simple_implementation` (`CI_LOOP_STAGE_TYPE_BY_STATUS`) -> `SimpleImplementationFinish` -> `opening_pr` (`pr_create`, `PrOpenedFinish` with `checks_follow: true`: the check posts a required GitHub status, so the commit must be pushed first) -> `ci_checking` (`ci_check`: a plain command, `Ci::CommandRunner` + `Ci::CheckPoller`, `CiCheckFinish` stores the log and exit status) -> `ci_verifying` (`ci_verify`: agent fixes, commits and pushes, then prints the marker read by `AiCli::Output#ci_verdict`; `CiVerifyFinish`) -> FAILED goes back to `ci_checking` until `Stage#completed_ci_rounds` reaches `project.ci_max_rounds`, then the workflow parks `errored` -> PASSED goes to `reviewing` (reviewers pinged), or `local_testing` when `project.local_test_ready?`. Prompt bodies: `app/services/prompts/defaults/{simple_implementation,ci_verify,pr_create}.md`. `Workflows::CiLoopResume` picks where an errored ci_loop workflow resumes (called from `Workflows::Transitions`). The ci_loop stage types are all in `LAZY_STAGE_TYPES`.

## Checklist (in order)

1. **Migration/enum values** (see `ai-worker-domain`). Enum integers are stored: append, never renumber.
   - The single `Stage::STAGE_TYPES` mapping in `app/models/stage.rb` (`PromptTemplate` reuses it, so there is one place to edit).
   - `Workflow` `enum :status` in `app/models/workflow.rb` (`local_testing: 11`).
2. **`StageRun::ACTIONS`** (`app/models/stage_run.rb`): add every action the new code will `log(...)`. Validation rejects unknown actions, so this comes before any handler code (`local_test_completed`, `local_test_failing`, `local_test_retest_scheduled`, `local_test_rounds_exhausted`).
3. **Stage helpers** (`app/models/stage.rb`): history queries the flow needs, e.g. `completed_local_test_rounds`, `local_test_unfinished?`. Use `last_action` (ordered by id), not the association's default `created_at desc` order.
4. **Workflow wiring** (`app/models/workflow.rb`):
   - `app/models/workflows/stage_resolver.rb`: `STAGE_TYPE_BY_STATUS` (jira projects; the status maps live only in `Workflows::StageResolver`). Also `SIMPLE_STAGE_TYPE_BY_STATUS` (personal) / `PR_REVIEW_STAGE_TYPE_BY_STATUS` only if those kinds reach the stage.
   - Same file, `LAZY_STAGE_TYPES` (jira_update, uat_test, local_test and the ci_loop types): a stage type not seeded at creation must be listed, otherwise `current_stage` returns nil and the scheduler silently skips the workflow.
   - Seeding is `app/models/workflows/stage_seeder.rb` (called from `Workflow`): only add the type there if every new workflow needs it up front (local_test is lazily created instead).
   - `Workflow#resume_status` (lives in `app/models/workflows/transitions.rb`; `Workflow` only delegates): where an `errored` workflow returns to (`:uat_testing`, `:local_testing` via private `local_test_unfinished?`). Without it a failure resumes into the wrong status.
5. **Prompt default**: add `app/services/prompts/defaults/<stage_type>.md` and its `Prompts::Defaults::DESCRIPTIONS` entry; details and the placeholder checklist are in the `ai-worker-prompts` skill.
6. **Result marker** (`app/services/ai_cli/output.rb`): one method per marker line (`local_test_result`, `retest_requested?`, `local_test_feedback_block`), anchored regex, take the **last** match (the log echoes the prompt's own example). The prompt body must tell the agent to print the exact marker.
7. **Start path** (a non-agent stage such as `ci_check` also needs a runner/poller choice in `Stages::RunTooling` in `app/services/stages/run_tooling.rb`, passed as `StageExecutor`'s `tooling:`: `PLAIN_COMMAND` is `Ci::CommandRunner` + `Ci::CheckPoller`, `AGENT_CLI` is `AiCli::Runner` + `AiCli::RunPoller`) (`Stages::StartHandler` in `app/services/stages/start_handler.rb`): add a `when "local_test" then start_local_test` arm in `#call`, and the `start_*` method. Validate config first (`AiCli::BrowserTestRun#validate!` raises `ArgumentError`, rescued by `StageExecutor#call` and handled by `fail_stage`), then its injected `AiRunLauncher#call` (or `start_browser_test`).
8. **Finish service** (`app/services/stages/completion_handler.rb`): `CompletionHandler#call` only dispatches; add a `when` arm that builds a new `Stages::<Type>Finish` (one class per stage type, e.g. `Stages::LocalTestFinish#call`) holding the completion logic. Parse the marker; a missing marker raises `AiCli::CommandError` so the stage fails visibly (rescued by `StageExecutor#call`). Put pure decisions in their own object: PR-check outcome in `stages/pr_check_decision.rb`, local-test retry/outcome rules in `stages/local_test_policy.rb`, best-effort reviewer notify/auto-merge in `stages/review_handoff.rb`. Failure handling (consecutive-failure cap, `errored`) is `stages/failure_handler.rb`; run polling/stale-kill is `ai_cli/run_poller.rb`.
9. **Scheduler** (`app/jobs/workflow_scheduler_job.rb`, queries in `app/services/scheduling/workflow_queries.rb`): add the new in-flight status to `WorkflowQueries::ACTIVE_STATUSES` (or `POLLING_STATUSES` for statuses entered outside the main loop, or a phase like `run_uat_phase` for time-gated ones), and to `BUSY_STATUSES` if the post-merge phase must not run during it (`work_in_progress?`). See `ai-worker-scheduling`.
10. **Views/controllers**: add the status to `WORKFLOW_STATUS_BADGE_CLASSES` in `app/helpers/workflows_helper.rb` (`badge-info` / `badge-success`; unmapped statuses render `badge-neutral`) and to `spec/helpers/workflows_helper_spec.rb`; both views use `workflow_status_badge`. Project-level toggles/fields go in `app/views/projects/_form.html.erb` and `ProjectsController#project_params`, plus `Project#local_test_ready?`-style readiness predicate. `PromptTemplate` forms list types from the enum automatically.

## Invariants

- Every logged action is in `StageRun::ACTIONS` first (step 2).
- Every finish handler ends its run with `workflow.finish_ai_run!(...)` (merges `Workflow::AI_RUN_RESET`: clears `processing`, pid, log path, offset). Forget it and the workflow polls a dead run forever. `Stages::FailureHandler` already does this; only the success paths are yours.
- A finish handler leaves the workflow in a status the scheduler picks up (or terminal). Check the status appears in step 9's lists (`Scheduling::WorkflowQueries`).
- Counting rounds/retries: cap them (`Stages::LocalTestPolicy::MAX_LOCAL_TEST_ROUNDS`) and log an `_exhausted` action rather than looping.
- New result markers get an `AiCli::Output` method **and** a spec; never regex agent output inline in `StageExecutor` or a handler.
- Handler-side effects that reach git/GitHub/Slack follow `ai-worker-orchestration` (argv arrays, rescue the typed `*::CommandError`).

## Specs to add (see `ai-worker-testing`)

- Model: `spec/models/stage_spec.rb` (helpers), `spec/models/workflow_spec.rb` (`current_stage` creating the stage via `LAZY_STAGE_TYPES`, `resume!` back to the new status, as in the "goes back to local_testing" example), `spec/models/workflows/transitions_spec.rb` (`resume_status`).
- `spec/services/ai_cli/output_spec.rb`: every marker method, incl. missing marker, case, and last-match-wins.
- Prompt specs (`spec/services/prompts/**`): see `ai-worker-prompts`.
- Handlers and decisions: `spec/services/stages/completion_handler_spec.rb` (dispatch), one spec per finish service (`implementation_finish_spec.rb`, `pr_check_finish_spec.rb`, `task_finish_spec.rb`, `pr_review_finish_spec.rb`, `jira_lifecycle_finish_spec.rb`, `local_test_finish_spec.rb`, `ci_check_finish_spec.rb`, `simple_implementation_finish_spec.rb`, `ci_verify_finish_spec.rb`, `pr_opened_finish_spec.rb`, `runbook_step_finish_spec.rb`; assert `AI_RUN_RESET` cleared, logged actions), `failure_handler_spec.rb`, `pr_check_decision_spec.rb`, `local_test_policy_spec.rb`, `review_handoff_spec.rb`; polling in `spec/services/ai_cli/run_poller_spec.rb` and `spec/services/ci/{command_runner,check_poller}_spec.rb`; `spec/services/stages/run_tooling_spec.rb`; `spec/models/workflows/{ci_loop_resume,current_stage}_spec.rb`; resolver maps in `spec/models/workflows/stage_resolver_spec.rb`. Prefer extracting new finish logic into a small testable object like these.
- `spec/services/stages/ai_run_launcher_spec.rb` covers detached launch state and runner options; `spec/services/stages/start_handler_spec.rb` covers dispatch through its injected launcher; `spec/services/stage_executor_spec.rb` covers the guard, polling and the rescue path. Stub the agent CLI, `Github::Client` and `Git::*` and assert the resulting `status`, cleared `Workflow::AI_RUN_RESET`, and logged actions.
